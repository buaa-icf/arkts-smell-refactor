# ArkTS 异味检测与重构

你负责对话中的结果解释和步骤衔接；检测、候选生成、验证和文件事务由已有后端执行。支持 Feature Envy、Long Method、Switch Statement、Code Clone。候选重构与独立评审仍由后端调用 DevEco Agent，不能把聊天中的建议当作已执行的重构或验证结论。

首次执行前阅读 [CLI 调用与结果约定](references/cli.md)。确定工具仓库 `backend` 和设置文件的绝对路径，以及设置中的 `projectRoot`。优先沿用本次对话或现有项目设置；仅在无法确定目标时询问。后端需要已完成 `npm ci`、`npm run build`，入口是 `<backend>/dist/skill.js`。Skill 可以安装在业务工程，命令仍使用工具仓库的绝对路径。

## 对话流程

1. **确定范围并检查环境。** 使用 `doctor`，报告缺少的能力。`canDetect` 与 `canRefactor` 分开看；可以检测但缺少重构环境时先完成用户要求的检测。用户指定文件或目录时沿用该范围，不自行扩大到整个工程。工具路径检查通过不等于 SDK、登录、签名或设备已经验证。
2. **检测或导入。** 使用 `scan`；已有报告则使用 `import`。保留返回的 `responseFile`，按 `issueId` 标识问题。用简短表格呈现序号、异味、文件/行号、问题概述和是否支持重构，并说明扫描范围。用户仅要求检测时，在这里给出结果和可选下一步。用户已指定问题或重构目标时继续，不重复询问已经明确的选择。
3. **准备并解释建议。** 用原 `responseFile` 和选定 `issueId` 调用 `prepare`，保存 `taskHandle`。读取返回风险和必要的任务材料，说明目标、建议调整、需要保留的行为及影响文件。业务约束写入 UTF-8 文本，使用 `--instructions-file` 传入。用户改变约束后重新准备；不要修改已有候选。检测证据过期时重新检测或要求用户提供新的报告，不能为绕过过期检查而重复导入旧报告刷新哈希。
4. **生成并审阅候选。** 用户选择生成候选，或已经要求重构该问题时，调用 `execute`。此步骤在隔离副本完成重构与后端验证。呈现最终 `verdict`、各门禁状态、关键 diff、变更文件和证据路径。重构建议是模型解释，实际变更以冻结候选为准。候选 `PASS` 仍不表示原工程已经应用。
5. **按选择应用或继续检查。** 用户可以查看完整 diff、补充要求重新准备、重新验证候选、应用或停止。应用前先展示当前候选的变更及验证结果；仅在用户已授权应用该候选或已明确授权相应范围的自动应用时，使用 `apply --candidate <id> --confirm <同一id>`。`--confirm` 是防止误选 ID 的命令参数，不是用户授权的替代物。不要直接复制候选文件或手动改原工程来绕过应用事务。
6. **应用后复检与反馈。** 应用成功后执行 `validate-applied`，分别报告候选验证、应用事务和原工程复检结果。原工程复检通过后，后端按原检测范围更新问题列表。失败或阻塞时解释实际证据，给出继续排查、重试或回滚的选择；不能把旧候选的 `PASS` 当作本轮通过。用户选择回滚时，调用对应候选的 `rollback --confirm <id>`，报告 `ROLLED_BACK` 或具体冲突；有后续修改的文件由事务保留，不强制覆盖。

## 跨轮次与恢复

- 在对话中保留设置文件、检测 `responseFile`、目标 `issueId`、`taskHandle` 和当前 `candidateId`；操作结果均有磁盘证据，不依赖记忆重建对象。
- `validate-candidate` 生成新的 `candidateId`，后续 diff、应用和授权范围均针对新候选，先展示新的结果。
- 新聊天或上下文缺失时先运行 `history`。仅对 `hasCandidate: true` 的记录使用其 `candidateId` 调用 `restore`，再根据候选和事务状态选择查看、复检或回滚；不能默认应用历史候选。扫描/准备记录没有候选：读取本工程 `runs/skill-results/` 中对应的 `responseFile` 继续，或从运行目录 `prepared.json` 找到 `taskHandle`；缺少完整检测结果时重新检测，不能把 `taskHandle` 当作候选 ID。
- 同一工程逐项执行。一次应用后，其他旧候选可能因基线变化失效；按后端错误重新检测/准备，不覆盖当前源码。

## 结果解释

`ok: true` 只表示命令正常完成。`PASS`、`FAIL`、`BLOCKED`、`INCOMPLETE` 以对应本轮后端结果为准；缺失证据、工具异常或空报告不能解释为通过。跳过的 Linter 应明确标为跳过，不能汇报“所有检查通过”。

后端已负责有限次数的代码返修；不要在聊天层无限重跑。环境、签名、设备、登录或超时阻塞时先报告原因及证据，等条件改变后再执行相关步骤。内层 Agent 的工具边界沿用后端设置，不为启用此 Skill 而解除内层 `skill` 工具限制。

每一步用用户可理解的结果说明已完成什么、还剩什么，提供与当前状态相符的下一步。最后交代原工程是否实际修改、验证结论、当前候选/事务状态和证据位置。
