# Agent 耗时优化与 7/15 分钟达标率

## 目标与状态

目标：same class 内修改的端到端耗时 ≤420 秒，跨类修改 ≤900 秒，达标率至少 70%。用户已确认计时包含首轮重构、修复和全部门禁，采用实验报告的 `totalSeconds`；不能用首轮 Agent 时间或各门禁耗时之和替代。

本轮实现包括提示词优化，以及用户补充授权后的可选 Linter 跳过策略。模型、超时和 token 配额未改；构建、测试、异味、公共契约和语义评审要求保留。2026-10-07 用户已复跑旧批次全部 9 个超时 LM 样本：9 条 PASS、零返修、6 条进入 7 分钟内；完整结果和统计限制见 [定向复跑分析](long-method-optimization-rerun-20261007.md)。结果分析后新增镜像路径修复、空白编辑约束和源码扫描的目录提前剪枝；其中风险扫描局部基准为 146.298s → 4.245s，风险报告与归档相同，新改动尚未做端到端复跑。

## 基线与统计口径

依据用户提供的两份实验报告：

- `../TestResult0915/code-clone-experiment-20260915.md`：27 条，采用报告指定的有效运行，包括 2026-09-16 的覆盖复跑。
- `../TestResult0915/long-method-experiment-20260918.md`：17 条，2026-09-17～18 的有效运行。

CC 的类别取有效运行 `task.json` 中检测消息的 `same method` / `same class` / `different classes` 标签：前两者归入同类；不能用“同一个文件”代替“同一个类”。LM 本批全部为原类内方法或 Builder 提取，按同类计算。这是复现原 18/27 口径的分类；部分检测消息与报告的中文描述不一致，若要校正类别，应在对照实验前根据原始所属类统一冻结，不能根据结果重新分组。

达标须同时满足最终 PASS 和耗时不超过对应阈值。本批 44 条最终均 PASS，因此基线只需比较报告中结果表的总耗时列。后续 FAIL/BLOCKED/未完成条目不能从固定样本分母中悄悄剔除。

| 分组 | 达标 / 样本 | 达标率 | 达到 70% 所需达标数 | 净缺口 |
|---|---:|---:|---:|---:|
| CC 同类 | 4 / 9 | 44.4% | 7 | 3 |
| CC 跨类 | 14 / 18 | 77.8% | 13 | 0 |
| CC 全部 | 18 / 27 | 66.7% | 19 | 1 |
| LM 同类 | 8 / 17 | 47.1% | 12 | 4 |
| 两批同类合计 | 12 / 26 | 46.2% | 19 | 7 |
| 两批总计 | 26 / 44 | 59.1% | 31 | 5 |

因此“整体达到 70%”需要净增加 5 条达标；“两类各自至少 70%”需要同类净增加 7 条，跨类守住已有达标样本。优化重点应放在同类和边界样本，不能只追逐最长的跨类任务。

## 报告支持的优化方向

Code Clone 的编辑前探索是重要成本。旧分析脚本给出首次编辑延迟中位数约 174 秒、读类调用均值 14.1 次，提示应减少重复定位、跨目录搜索和无依据的方案枚举。但相关性不证明因果，也不足以推出统一的读取次数上限。

Long Method 首轮 Agent 合计 2991.584 秒，占端到端 30.9%；修复 Agent 为 1973.234 秒，占 20.4%。17 条中 3 条首次失败均为 Linter：LM-011 的私有方法命名，LM-014/015 的格式与 ForEach 规则。LM-014 在修复中新增 index-only key 造成语义回归，最终第三轮修复耗时 1150.708 秒。因此不仅要缩短首轮，还要避免为赶首轮而增加返修。

不能把三条 ArkTS 预置提示描述为覆盖所有返修：CC-002/003 还有可见性、命名、分号问题，CC-005/014 还有残留克隆；Long Method 的主要返修原因也不是 `@Param`。

### 原统计的局限

旧文档引用的 `v/clone-series-logs/agent-profile2.py` 和 `agent-phase.py` 只把 `edit/write/patch` 当作编辑。CC-019 实际通过 `bash` 中的 `Copy-Item` 将三个历史实现文件复制进工作区；对应 `refactor-changes.json` 也列出了三个生产文件。因此“零编辑”仅表示没有这些工具事件，并不表示没有写入。

可核对的原始证据位于 `runs/20260916-111611/code-clone-0001-EditNamePage/` 的 `refactor-agent.log`、`refactor-changes.json` 和 `result.json`。该日志还包含路径定位失败、工作区外历史目录探索和历史实现复制，不能把 1165.894 秒首轮时间全部归因于必要的重构推理。

旧脚本的首次编辑计时从首条日志事件起算，而不是进程启动时刻；漏识别 shell 写入还会影响编辑前/后 token 划分。旧版 64% 编辑前时间、76.2% 编辑前思考量等数值只作待校正的探索线索，不作为验收指标。本次未修改这些历史分析脚本，也未修改外部实验报告。

## 已实施的提示词调整

### 1. 用建议形态减少选型，而不是把画像当作证明

优先采用已有建议，与当前源码核对后即实施，不枚举无关备选方案。画像缺失、未解析或不适用时，允许选择最小重构。保留公共契约、模块依赖方向与行为等价要求。

源码中的 clone 画像本身明确是词法分析，且允许对照片段未解析；当前实现也没有专项 `longMethodAnalysis`。因此不能要求所有任务直接相信画像、不校验行号，或在画像缺失时仍遵守不存在的修改边界。

### 2. 用证据限定探索，不设 6 次读取硬上限

优先批量读取目标、检测器对照片段、画像关联文件；信息足够后立即编辑。仅在证据缺失时定向读取隔离工程内的直接类型、导出或共享实现，不扫描无关相似代码。

修复轮把 `issues[].filePath` 和 `changedProductionFiles` 放在优先列表前部，即使没有 `logTail` 也有效；允许复读新建 helper，并提醒原画像行号可能漂移。God Class 调用者和循环依赖边证据也进入列表，避免公共提示词误限制其他异味。

路径以当前隔离工程根目录为基准；禁止到原仓库、历史 runs 或快照中搜索或复制实现。取消“读满 6 次立即编辑”，避免缺少证据时盲改，以及为了少算工具次数改用 shell 大段读取。

### 3. 编辑完成再验证，首次通过即停止

保留全部实例编辑完成后再验证。`build_project` 与 `arkts_check` 每轮合计最多 2 次：按改动选择一种必要验证，首次通过即停止；仅在首次失败被确认是本轮引入的编译/静态检查缺陷时，修复后再验证一次。

首轮和修复轮共用同一段约束，消除原先“build 最多两次”和“两工具合计两次”的双重描述。任一次出现环境错误都停止内部验证。平台完整门禁照常执行。

### 4. 针对报告里的返修原因预防缺陷

- 沿用目标文件的可见性、命名和局部格式，包括已有私有方法的下划线、分号、尾逗号、对象属性换行；不全文件格式化。
- 保留 ForEach/LazyForEach 原有 keyGenerator，包括原本没有 key 的情况；不能为过 Linter 顺手添加 index-only key。
- 保留 `@Param`/`@Require`、组件输入约束和显式具名导出提示，不通过补默认值改变行为。
- Long Method 优先在原 class/struct 内按职责提取私有方法或成员 Builder，保持表达式和属性链。
- Code Clone 检查各入口是否仍有重复骨架，同时保留实例差异，减少 CC-005/014 式返修。

上述探索与内部验证约束由提示词表达，并非新增的工具拦截、访问控制或计数实现。没有新增时间/token 硬预算；Linter 的显式跳过则由下述流水线逻辑实施。

## 用户授权后的 Linter 策略

甲方已确认 Linter 属于加分项，返修严重时可以跳过。两份报告中 CC 有 4 条首次失败于 Linter，LM 的 3 条返修任务也都首次失败于 Linter，满足优先尝试跳过的依据。主要收益来自避免其触发的修复和重跑门禁，单纯少运行一次 Linter 通常只省几秒到二十秒。

- 通用 `start` 新增 `--linter-mode required|skip`，默认 required，保持既有行为。
- 本机两份实验脚本默认 `-LinterMode skip`，传 required 可恢复。它们原本被 `.gitignore` 忽略，本轮仅在本机修改；可复用实现仍在受版本控制的 CLI/runner 中。
- 手动 pipeline 配置支持顶层 `"linterMode": "skip"`。仅缺失或禁用 Linter 配置仍保留原来的 INCOMPLETE 行为，避免把环境缺失误当作豁免。
- skip 模式下不调用 Linter、不生成其失败报告或修复轮；步骤记录 SKIPPED 而非 PASS。`gates.json`、`result.json` 及自动运行的 `summary.json` 记录 `validationPolicy.linterMode`。
- 首轮与修复 Agent 得到明确跳过说明，语义评审读取实际策略，不因纯格式/命名问题重新引入 Linter 返修；真实行为变化仍阻断。
- 其他必需门禁失败、缺失或语义评审失败仍阻断或触发相应修复，不能被 skip 旁路。

CC-027 的历史 Linter 用时 5.749 秒，大于它距 7 分钟线的 2.421 秒差距；其他耗时不变时，仅省这一步就可能转为达标。但多数 LM 边界样本不能仅靠少跑几秒 Linter 达标，仍需要提示词优化；对原先被 Linter 提前拦下的版本，不能假定未执行的语义评审一定通过。

这是甲方允许的验收配置变化，必须与单纯提示词提速区分。若需要分别归因，应保留“旧提示词+required”“新提示词+required”“新提示词+skip”三种配置的结果。

## 恢复 Linter 时的项目规则提示

根据用户提出的预防风格返修方案，required 模式现在在首轮和定向修复 Prompt 中自动注入 `code-linter.json5` 的显式风格规则摘要。配置查找与自动门禁共用同一个函数，从目标目录向仓库根查找最近配置，因此模板仓会定位到 OfficeAttendance、ComprehensiveMall 等具体 ArkTS 应用根目录；不会使用兄弟项目或仓库外的配置。

摘要保留命名选择器及私有成员前导下划线、可见性例外、分号、尾逗号、引号、成员分隔符等原始选项，以及 files/ignore、ruleSet 和条件覆盖项。提取器只摘录 JSON5 数据，不执行配置内容、不把注释当作指令；未能提取时明确说明缺失，实际 Linter 门禁仍照常运行。skip 模式不读配置、不注入摘要。

这是显式规则摘录，并非完整生效配置：没有展开安装版本内 ruleSet 的继承规则和默认选项。提示明确不能为满足风格要求改变公共 API、ForEach 键或其他运行行为。LM-011/014/015 对应的真实配置各提取出 16 条风格规则，摘要约 2,000 字符；没有额外调用模型或构建。代码回归为 103 项通过，尚无恢复 Linter 后的新端到端数据，不能据此断言与 skip 同速或返修归零。应优先用这 3 条历史 Linter 返修样本、相同源码基线和 `-LinterMode required` 验证。

## 按达标缺口安排复跑

先验证下列同类边界样本。表中“需节省”仅为总耗时与 420 秒之差，不是预测收益。

| 样本 | 基线总耗时 | 需节省 | 针对方向 |
|---|---:|---:|---|
| CC-027 | 422.421s | 2.421s | 跳过 Linter，减少重复定位与验证；极接近阈值，必须注意运行波动 |
| LM-005 | 433.002s | 13.002s | 直接在原 struct 内提取，减少无关方案探索 |
| LM-001 | 435.371s | 15.371s | 同上，保留状态与回调边界 |
| LM-016 | 457.931s | 37.931s | 保留匿名 Builder 上下文和 key 语义 |
| CC-017 | 463.571s | 43.571s | 按已知实例和差异直接实施 |
| CC-003 | 477.202s | 57.202s | 跳过 Linter 及其格式类返修 |
| LM-008 | 481.676s | 61.676s | 减少首轮选型和重复验证 |

前 5 条全部稳定转为达标且原达标样本不回退时，整体为 31/44（70.5%）；7 条全部转为达标时，同类为 19/26（73.1%）。这只是最低样本数量推导，不是效果承诺。

LM-011（629.202s）作为“避免命名返修”的备选收益样本；LM-014 作为 ForEach 行为约束的质量回归样本。跨类先用 CC-010（953.779s）验证 `@Param` 提示，避免一开始只复跑 CC-014/019 这类远超阈值且证据复杂的长尾样本。

只优化首轮有明确上限：LM-001/005 若其他耗时不变，首轮需分别降低约 9.5%/7.1%；LM-016/008 需约 20.1%/24.3%。LM-011 需要节省的 209.202 秒甚至大于其首轮 165.837 秒，只压缩首轮无法达标，必须减少返修或其他环节。

## 验证与验收

代码验证：设置 `PYTHONPATH=src` 后执行 `python -m unittest discover -s tests -v`，加入规则摘要后的版本为 103 项通过。新增回归覆盖无画像对照片段、无日志尾部的新增修复文件、架构类上下文、首轮/修复轮的 key 语义约束、Linter 跳过后的 Review/修复/必需门禁行为、嵌套 Harmony 工程的附件路径转换、保持文件集合的目录剪枝，以及 JSON5 风格摘要和门禁配置定位一致性。两份本地 PowerShell 脚本通过语法解析，CLI help 已确认暴露 required/skip 开关。

已有上述 9 条定向复跑，尚未完成新版本的全批验收。对照实验应固定代码基线、模型、SDK 和类别标签，记录提示词版本与 linterMode；比较提示词时保持门禁相同，比较 skip 策略时单独列出配置差异。先用上述样本判断方向，再用固定的全部 44 条重新验收；选择性复跑不能替代全批新达标率。

本机整批验收命令（各自按预运行快照回滚生产源码）：

```powershell
.\tools\run_code_clone_series.ps1 -StartOrdinal 1 -EndOrdinal 27 -LinterMode skip
.\tools\run_long_method_series.ps1 -StartOrdinal 1 -EndOrdinal 17 -LinterMode skip
```

每条至少记录：最终 verdict、totalSeconds、首轮 Agent 秒数、修复轮数、首次失败门禁、内部 build/check 调用数。首改延迟和 token 只用于解释原因；统计写入时需要覆盖 shell 文件写入、失败工具调用等情况，不能继续把“没有 edit 事件”等同于“没有改动”。

报告整体、同类、跨类以及两种异味的达标率，并单独列出原本达标而退化的样本。边界样本需重复运行观察波动；不得挑最快的一次替代预先约定的统计口径。现阶段不保留旧版“预计提速 15–30%”“预计 23–24/27 达标”的无对照实验估计。
