# Long Method 定向复跑分析（2026-10-07）

## 结论与口径

本轮复跑旧批次全部 9 个超过 420 秒的 Long Method 样本：001、005、008、009、011、013、014、015、016。9 条全部 PASS，repairAttempts=0、reviewRetries=0，Linter 均显式 SKIPPED，其余已启用门禁均 PASS。每条只修改一个生产文件，无 rejectedFiles，用户提供的终端记录确认全部回滚。

本轮 7 分钟内达标 6/9（66.7%），旧批次这 9 条为 0/9。这是针对原超时样本的定向复跑率，不是全体 17 条的新达标率。

端到端时间取用户粘贴的 RESULT 行 `totalSeconds`；阶段耗时、通过状态与修复次数取各任务的 `result.json`。旧值取 `../TestResult0915/long-method-experiment-20260918.md` 指定的有效运行。9 个目标文件的新旧 `pre-run-production-baseline/files/` 内容均逐字节一致；这不代表整个依赖环境和模型服务条件完全一致。

## 改善来自哪里

首轮 Agent 合计仅从 2029.596 秒降到 1924.084 秒，减少 105.512 秒（5.2%）；7 条变快，LM-013/015 变慢。因此端到端改善不能概括为“首轮 Agent 提速 40%”。

旧批次 LM-011/014/015 合计触发 5 轮修复，修复 Agent 累计 1973.234 秒；本轮全部为零修复，并避免了相应重复门禁。LM-014 从 2319.975 秒降到 349.617 秒，是最大的单项收益。Linter 跳过和提示词同时变化，加上模型运行波动，本实验不能单独分离两种调整的因果贡献。

内部验证调用由旧首轮 27 次（build_project 17、arkts_check 10）降到 10 次（各 5），减少了重复工具选择和错误后的探索。新的 5 次 build_project 调用全部报 `An error occurred in Effect.tryPromise`，但平台 build 均 PASS，说明内部工具调用失败与实际工程构建结果需要区分。LM-015 在该错误后又调用了 arkts_check，提示词的停止约束并非工具层强制保证。

## 剩余问题与新增修正

### 路径前缀错误：9/9 复现

所有本轮 refactor-agent.log 都至少有一次目标文件 File not found。以 LM-015 为例，Agent 工作区根目录已经是 OfficeAttendance，实际路径从 `scenes/schedule/` 开始，提示词却仍给出 `BusinessTemplate/OfficeAttendance/scenes/schedule/...`。

根因是 prompts.py 已将路径转换为仓库相对路径，但 refactor_gate 仍只替换带仓库名前缀的原始 `task.target.file_path`，替换失效。已在 gate 附件生成时根据实际 source_root 统一转换仓库相对、工作区相对和绝对路径，涵盖目标、对照片段和修复 helper，并保留其他工程路径及原始归档提示词不变。新增测试覆盖首轮、修复轮、不同分隔符与相似目录名前缀。

### 文本编辑反复失败：LM-013/015

| 样本 | 旧首轮 Agent | 新首轮 Agent | 本轮日志证据 |
|---|---:|---:|---|
| LM-013 | 320.388s | 358.250s | 7 次 edit，其中 3 次 oldString 不匹配；6 次 bash，反复检查 CRLF、空白行数和清理空行 |
| LM-015 | 279.712s | 453.127s | 15 次 edit，其中 4 次 oldString 不匹配；先清理空白块，反复猜测 18 行空白，随后才执行主要提取 |

LM-015 的推理 token 从 7844 增至 23393。缺少 Linter 返修掩盖了首轮编辑效率退化：端到端仍改善，但首轮实际上更慢。

已给首轮/修复提示词补充：不为提取先清理原空白或转换整个文件换行；采用唯一非空代码锚点；oldString 失败后依据当前实读文本缩小替换，不反复猜测空行；保留原编码和换行。其效果尚未端到端复跑，不能计入上表成绩。

### 门禁计时以外的开销

本轮 `totalSeconds - sum(steps.duration_seconds)` 为每条 98.295～138.657 秒，中位数 101.100 秒，合计 973.886 秒（约占本轮总耗时 24.1%）。这部分不能算成 Agent 推理，也不能只凭差值全部归因于复制或风险扫描。

进一步对 LM-009 的 `analyze_risks` 做只读 cProfile，发现旧版一次耗时 146.298 秒，其中源码枚举累计 140.666 秒。旧实现 `root.rglob('*')` 会先遍历依赖、构建缓存等子树并调用 is_file，再判断路径是否含忽略目录；约 392,914 次 is_file 检查之后，实际只产出 6,682 个源码文件。

已改为 `os.walk` 在进入子目录前排除原有忽略项（.git、build、node_modules、oh_modules、.hvigor、.test），保留原有文件类型、大小写和测试源码发现规则。不是缩小有效源码或调用点扫描范围，也不新增缓存。

| 同一目标的局部测量 | 修改前 | 修改后 |
|---|---:|---:|
| analyze_risks（cProfile 开启） | 146.298s | 4.245s |
| 源码枚举累计时间 | 140.666s | 1.067s |
| 有效源码文件数 | 6,682 | 6,682 |
| 生成风险报告与原运行归档比较 | 原逻辑 | 完全一致 |

这组局部测量受文件系统缓存、机器负载和 profiler 开销影响，不能把 142.053 秒直接从历史 totalSeconds 扣除当作新的验收结果。它证明了一个可消除的目录遍历成本，实际端到端收益仍需新版本复跑。原始局部测量输出保存在本机 `.codex_tmp/lm-risk-profile-20261007-before.txt` 与 `lm-risk-profile-20261007-after.txt`。
